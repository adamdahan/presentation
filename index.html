Internal Proposal01 / 21

A self-maintaining documentation system

Work it out once.
Everyone gets the answer.

One written explanation per feature, shared by everyone. It notices when the code underneath it changes, corrects itself overnight, and is honest about it in the meantime.

Adam Dahan

The Problem02 / 21

Understanding one feature means crossing the whole system.

A card purchase arrives on a webhook, moves across a queue, through a service, out via an API, and up into a mobile screen. Neither codebase says those pieces are connected. You only find out by opening both and working it out.

So every developer works it out from scratch, ships their ticket, and forgets it. The next person starts over. And front-end developers rarely open the backend at all — they learn the half they can see and stop where the API starts.

The Problem03 / 21

Working it out from scratch is expensive. Reading it is not.

Working it out from scratch, every time~200,000 tokens · minutes · quality varies each time
Reading an explanation someone already wrote~4,000 tokens · seconds · identical every time

A hundred lookups the current way costs roughly 20 million tokens and produces a hundred slightly different answers.

Writing the analysis once and reading it a hundred times costs about 600 thousand — 200 thousand to do the work, plus 4 thousand a lookup — and everyone gets the same answer.

Every figure on this slide is an approximation. They come from watching real sessions, not from precise measurement. The point is the scale of the gap, not the exact digits — halve them and it is still about twenty-five to one.

The new repository holds one written explanation per feature, a list of everything in it, and a short instruction file that tells Copilot how to search that list.

To read them — nothing to set up

The documents are copied into mobile and backend automatically. You clone what you always cloned and they are simply there. Ask Copilot a question and it uses them.

To write one — open all three together

Double-click a single workspace file and VS Code opens all three folders side by side. That is the whole setup, and it is what lets the assistant read both codebases and write to the third.

Nobody is asked to install anything, and nobody needs to remember a second repository exists. Reading is automatic. The workspace only matters for the small number of people writing a document on any given day — and for them it is one double-click, once.

When To Write One05 / 21

Not every feature deserves a document.

Write one when

  • You had to open both repositories to answer the question.
  • The trail went cold where two systems meet — a queue, an outside service, a feature flag.
  • You designed something new that spans mobile and backend.
  • An incident taught you something the code does not say.
  • Someone has now asked you the same question twice.

Don't bother when

  • The whole answer lives in one repository, in a straight line.
  • An assistant gets it right by reading a single file on demand.
  • It's a rename, a config value, or anything already obvious from the code.

Writing down what the code already makes obvious is wasted effort — it goes out of date and buys you nothing. Writing down how systems join up, and what has bitten people keeps paying back, because you cannot get that from reading the code.

Built To Grow07 / 21

Three decisions that stop this collapsing at five hundred documents.

1

We look documents up in a catalogue. We never read the catalogue.

A librarian doesn't read every card to find one book — they look up the entry. Our index is one line per document, built to be searched rather than read, so finding the right document costs the same whether there are twenty of them or twenty thousand.

index/manifest.tsv — one tab-separated row per document (path · kind · domain · repos · status · keywords). The skill runs grep and receives matching rows only. Retrieval is O(matches), never O(corpus).

Same cost at any size
2

We ask each codebase one question a night, not thousands.

Instead of asking "has this file changed?" once per file, we ask each codebase for its complete inventory in a single request and compare it ourselves. Five thousand questions a night becomes two — and it stays two as the number of documents grows.

Git Trees API — GET /repos/{owner}/{repo}/git/trees/{ref}?recursive=1 returns every blob SHA in one response. We build a path→SHA map and diff it against the recorded fingerprints in memory. O(repos), not O(files); falls back per-file when the API sets truncated: true.

Two requests, always
3

A document carries labels. It is not defined by which drawer you put it in.

If a folder name is the only label, a document can only ever be one thing — and changing your mind means moving files and breaking every link to them. Ours carry labels written inside the file, so the same document can be found several ways, and changing your mind costs one word.

kind · domain · repos · keywords live in YAML frontmatter; the manifest is generated from it. Any axis is filterable — awk -F'\t' '$3=="payments"' — and CODEOWNERS on a domain folder routes review without touching the taxonomy.

Cheap to change

None of this is optimisation for later. A system that gets slower and more expensive the more people use it punishes its own success. It gets quietly abandoned at exactly the point it had started to matter.

The Moving Parts08 / 21

Four pieces. Each one does a single job.

None of this is a plugin or a product. They are ordinary files that live in the repository, and every assistant that opens the folder reads them.

Always on · reading

copilot-instructions.md

Copilot reads this on every single question, automatically. It says: search the list first, open only the one document that matches, check whether it is still trustworthy, and say where the answer came from. Nobody types anything to switch it on.

Without itYou get an answer from whichever half of the system happens to be open.

On demand · writing

/trace

You just built something. Type /trace and it reads your changes across both repos, follows the whole path, asks what bit you, and writes the document. Name a feature instead — /trace creating a todo — to write up code that already exists.

Without itContributing means learning a procedure, so nobody contributes.

On demand · fixing

/verify

Re-checks a document against the code, quotes back every sentence that has stopped being true, fixes them, and updates the fingerprints. Use it on anything flagged, or to confirm an overnight repair before approving it.

Without itA flagged document stays flagged until someone does it by hand.

Unattended · maintaining

The repair job

The same work as /verify, running overnight without being asked. It reads the code change beside the old explanation, rewrites what is no longer true, and opens a small pull request addressed to whoever made the change.

Without itDocuments rot quietly, which is how documentation always dies.

Read · write · fix · maintain. Only two of them require a person, and both are things you are already in the middle of doing.

How It Works · The Document10 / 21

Every document records the code it was written from.

The top of the file is written for the computer, not for you. It lists the exact source files the explanation was based on, and stores a fingerprint of each — a short code Git already calculates from a file's contents.

Change one character in any of those files and its fingerprint changes. Compare the fingerprints and you know whether the code has moved since somebody wrote this. That is the whole trick.

The fingerprint is the file's git blob SHA — SHA-1 of "blob <size>\0" + contents. Content-addressed, so it moves if and only if the bytes move.

It is not the commit SHA. Commits elsewhere in the repository leave it untouched, so a document is only flagged when the code it actually describes changes.

git hash-object <file> and the GitHub API return the identical value — which is why the same check runs on a laptop and in CI with no code change. Git already computes it for every file, so verification costs nothing to produce.

How It Works · Honesty13 / 21

We don't promise the documents are fresh. We promise they say when they aren't.

Verified

Fingerprints match, and it was written with both repositories open.

Stale

The code has changed since this was written. It may still be perfectly correct — somebody may have only reformatted a file — but nobody has checked, so do not lean on it yet.

Needs review

The system has caught up with the code, but no one has re-read the words against what changed. Treat it exactly like stale — a refreshed file is not a checked one.

One-sided

Written by someone who only had one of the two repositories open. Trust what it says about that side; treat the rest as an educated guess.

Open one of these and Copilot tells you the status before it answers. Being out of date then costs you a warning sentence instead of a bad decision.

Questions · Your Repositories20 / 21

What this does to the repo you already work in.

Q

Does this bloat our repository?

The documents are plain markdown. Each sync commits a few changed lines, not a new copy of the folder — so history grows by the size of the edit, the way any text file does.

Measured on the live system28 KB today · about 1 MB at five hundred documents. The lockfile sitting beside it is 576 KB.

Q

Does it ship inside our app or our image?

No — but not because it is hidden from git. It is committed, which is exactly how you get it on clone. It is excluded from the things you build: the bundler only packages what the code imports, and nothing imports markdown.

Backend, where COPY . . would have caught itThe sync adds the folder to .dockerignore, .npmignore and .easignore — appending, never overwriting yours.

Q

Will it collide with my pull request?

The sync commits on its own branch and only ever touches the docs folder and the Copilot instructions file. You touch source. Two changes to different files merge without a conflict — your branch simply sits one commit behind, which it already does every day.

One open PR per repoIt updates in place as documents change, rather than opening a new one each time.

Q

What if someone edits the mirrored copy?

That is the one real hazard: the next sync overwrites it and their work vanishes with no explanation. So a check fails the pull request and comments with the files and where to make the change instead.

Fails loudly, on purposeSilent overwriting is how a team concludes the system is broken.

Questions · Trust & Cost21 / 21

What it costs, and what happens when it is wrong.

Q

What if a document is simply wrong?

The instruction every assistant reads says the code wins. When a document and the codebase disagree, it trusts the code, says so out loud, and flags the document. And every answer opens by naming its source and its status, so a reader is never guessing whether they got an analysis or a guess.

The honest promiseNot that the documents are always fresh — that they tell you when they are not.

Q

Who writes five hundred documents?

Nobody, up front. A document gets written when someone has just finished tracing a feature across repositories — the analysis already exists in their head, and we capture it instead of losing it. Lookups that find nothing become the backlog.

Coverage follows demandThe features people actually ask about are the ones that get documented first.

Q

What does the checking cost to run?

The nightly check is one request per code repository — not one per document. It asks GitHub for every file fingerprint in a single request and compares locally, so ten documents and ten thousand cost the same.

ApproximateThe rewriting agent only runs on documents that were actually flagged, and needs one API key.

Q

Can the agent change a document on its own?

No. It opens a pull request, assigned to whoever changed the code, quoting their diff and listing every sentence their change made untrue. Nothing merges without a person. If the rewrite leaves anything unresolved, the document stays flagged rather than being stamped correct.

Roughly thirty seconds of reviewSpent on work you still have in your head.
