What every file does, in the order it happens.

There is no single top-to-bottom order — there are three separate chains, and which one runs depends on what somebody just did. Only one file in the whole system uses an AI, and it is the last one in the last chain.

Chain 1 · Somebody asks a questionall day, every day

“How does completing a todo work?”

Typed into Copilot Chat. No command, nothing to remember.

#FileWhat it does
1 .github/copilot-instructions.md The rulebook Copilot reads before every single answer. Nobody switches it on. It says: search the list first, open only the one document that matches, check whether it is still trustworthy, and tell the person where the answer came from.
2 index/manifest.tsv The card catalogue. One line per document — where it lives, what it covers, and the words somebody would search for. Copilot searches this and never reads the whole thing, which is why a lookup costs the same with 20 documents or 20,000.generated
3 docs/<area>/<name>.md The actual explanation. One file is opened. The others are never touched.
— .github/skills/…/SKILL.md A spare copy of the same rules, in the format some AI tools expect instead of an instructions file. Belt and braces — whichever one the tool reads, it gets the same procedure.
Chain 2 · Somebody writes a documentoccasionally, and voluntarily

They just built a feature and typed /trace

This is the only chain that needs the three-folder workspace.

#FileWhat it does
1 .github/prompts/trace.prompt.md The /trace recipe. Tells the assistant exactly how: look at what changed in both repos, follow the whole path through the code, ask the person what surprised them, then write the document along with the list of code files it was based on.
2 tools/build-index.mjs Rebuilds the catalogue. Reads every document and writes out manifest.tsv, watchers.json, and the table in the README. Run at the end of /trace so the new document is findable straight away.
3 .github/workflows/build-index.yml Does that again automatically once the change is merged, in case somebody forgot. The catalogue is never allowed to be hand-edited or out of date.
4 .github/workflows/mirror-docs.yml Copies everything into the app and server repos so developers get it without downloading anything new. Also keeps it out of the shipped app and stamps the copies read-only.
— README.md The human-readable index. Generated, not written — it used to be kept by hand and quietly went out of date, so now it is built from the documents themselves.generated
Chain 3 · Somebody changes codeall day, every day

This is the half that keeps the documents honest.

Nobody asks for any of this. It happens because code moved.

#FileWhat it does
1 index/watchers.json A reverse lookup: “which documents rely on this file?” Used the moment a pull request opens, to comment telling the author which explanations their change affects. It asks nothing of them.generated
2 templates/docs-guard.yml A guard installed in the app and server repos. Stops somebody editing the mirrored copies — those get overwritten, so their work would silently vanish. Fails the pull request and points them at the right place instead.
3 .github/workflows/check-fingerprints.yml The alarm clock. Runs the checker below on a schedule — or the moment code merges, if you would rather not wait for the night.
4 tools/check-fingerprints.mjs The checker. Every document lists the code files it was written from plus a fingerprint of each. This asks GitHub for the current fingerprints — one request per repository, not one per file — and compares. Anything that moved is marked out of date.no ai
5 .github/workflows/repair-documents.yml The repair job. Runs the two below, then opens a single pull request.
6 tools/propose-repair.mjs Works out what changed and who did it. Updates the fingerprints, pulls up the real code diff, and finds who last touched the file so the review lands on the right person. Marks the document “needs review”, never “verified” — refreshing a fingerprint is not the same as somebody having re-read the words.no ai
7 tools/agent-repair.mjs The only file that uses an AI. Reads the code change beside the old explanation and rewrites the sentences that are no longer true — quoting each one back, so you can see exactly what people had been believing. Only this can promote a document to “verified”, and only when nothing is left unresolved.ai
— .github/prompts/verify.prompt.md The /verify recipe — the same job as steps 6 and 7, done by hand in the editor when you want it now. This is what you use instead if you would rather nothing ran unattended.

Steps 4, 6 and 7 are three separate things, and only the last needs an AI. Drop step 7 entirely and you still get the detection, the flags, the refreshed fingerprints, and a pull request quoting your own diff, assigned to you. You would just fix the wording yourself — with /verify, in the editor, using the Copilot seat you already pay for.

Two folders you never touchrebuilt every time

index/manifest.tsv

Document → where it is, what it covers, what to search for.

Answers “where do I find out about X?”

index/watchers.json

Code file → which documents depend on it.

Answers “if I change this, what goes out of date?”

Same information, pointing in opposite directions. Both are generated from the documents on every change — neither is ever edited by hand, because a hand-maintained index is exactly the thing that silently drifts and stops being trusted.

The one-paragraph version—
CountWhat
3instruction filesTell an AI what to do — one for answering questions, one for writing a new document, one for fixing an old one.
4small scriptsDo the mechanical work — build the catalogue, check the fingerprints, work out what changed, rewrite the prose.
4workflowsDecide when those scripts run — on merge, on a schedule, or on a button.
1needs an AIAnd it is the last one in the chain. Everything before it is plain comparison.

No plugin, no product, no licence. Ordinary files sitting in a repository, which is why every assistant that opens the folder picks them up without anyone installing anything.
